## 1. Что в проекте сделано хорошо (не трогать)

Это не вежливость, а границы работ: перечисленное ниже переживает рефакторинг
без изменений.

- **`core/domain/` не знает о хранилище.** Правила выражены константами и
  чистыми функциями, миграция с заглушек на PostgreSQL их не тронула. Это
  единственный слой, который доказал свою стоимость на практике.
- **`core/links.py`** — `CatalogState` (frozen dataclass) + один список осей
  `CATALOG_AXES` на проект. URL-состояние каталога решено правильно.
- **`core/queries/catalog.py`** — выдача честно живёт в QuerySet: аннотации
  (`effective_chars`, `read_minutes_db`, `in_open_contest`), объём подзапросом,
  а не `Sum` по join. Пагинация на уровне БД.
- **Пакет `core/views/`** — модуль на раздел, имена собраны в `__init__`.
- **`Story.apply_moderation`** — статус и уведомление одним движением.
- **Индексы (0008) и `pg_trgm` (0009)** поставлены под реальные запросы страниц.
- **Тест бюджета запросов** (`test_query_budget.py`) — самый ценный файл в
  суите; он один нашёл 59 запросов на профиле.

## 2. Диагноз: чем болеет кодовая база

### 2.1 Главная проблема — функциональная, а не архитектурная

**Половина write-путей продукта не существует. UI для них есть.**

| Кнопка / поведение в UI | Что происходит на самом деле |
|---|---|
| «Сақтау» (в библиотеку) | `LibraryEntry` пишется **только сидом**. Кнопка — Alpine-состояние в браузере. |
| «Жазылу» (подписка на автора) | `Follow` пишется **только сидом**. |
| Счётчик оқылым | `Story.views` / `recent_views` **не инкрементируются нигде**. |
| Прогресс чтения «X / N» | `ReadingProgress` пишется **только сидом** — не двигается. |
| «Барлығын оқылды деп белгілеу» | `Notification.read` не выставляется **нигде** вне корпуса. |
| `Story.chapters` (число частей на карточке) | `save_chapter` его **не обновляет**. Автор пишет 5 глав → карточка говорит «0 бөлім». |

Следствия каскадом:
- дефолтная сортировка каталога («Қазір танымал» по `recent_views`) в проде
  будет вечно показывать порядок из сида;
- витрины тегов (`usage_count` / `weekly_count`) тоже не пересчитываются
  (известный долг DEC-31);
- **демо-корпус на 1 361 строку — это протез вместо функциональности.** Он
  такой большой именно потому, что заменяет ненаписанные write-пути. Отсюда же
  50 тестов `test_corpus.py`, сторожащих целостность литералов.

Это первое, что надо чинить: любая оптимизация вокруг остаётся полировкой
неработающего.

### 2.2 Слой данных: два несовместимых контракта под одним фасадом

`core/data.py` экспортирует 133 имени. Часть возвращает `QuerySet`
(`catalog.py`), часть — `list` (`author.py`, `profile.py`, `contests.py`,
`story.py`, `tags.py` — 17 мест `return list(...)`).

У списка нет кэша и нет ленивости. Вызывающая сторона этого не видит, зовёт
хелпер столько раз, сколько удобно читать, — и профиль стоил **59 запросов**.
Лечение выбрали компенсирующее: класс `AuthorFacts`, снимок на один запрос,
который надо не забыть передать параметром `facts=` в **девять** хелперов.

Это лечение симптома. `AuthorFacts` — костыль поверх решения «фасад отдаёт
list». QuerySet кэширует себя сам, лениво, без параметра.

### 2.3 Скрытый контракт «аннотация или fallback»

Семь свойств моделей написаны так:

```python
annotated = getattr(self, 'effective_chars', None)
if annotated is not None:
    return annotated
return sum(c.char_count for c in self.chapter_set.all())   # N+1
```

(`works_count`, `has_any_chapter`, `in_open_contest`, `effective_chars`,
`submission_count`, `_my_reaction`, `_my_vote`)

Проблема: контракт между `queries/` и `models.py` **невидим и не проверяем**.
Забыл аннотацию — страница работает, но делает N запросов. Или, хуже,
`_my_reaction` молча отвечает «голоса нет», хотя голос есть. Ловится только
`assertNumQueries` — то есть постфактум и только на тех страницах, что внесены
в бюджет.

### 2.4 Толстая модель: 1 777 строк, из них 870 кода

`Contest` — 26 свойств. Часть из них делает запросы при каждом обращении:

```python
@property
def awards(self):        return list(self.award_set.all())
@property
def awards_by_slug(self): return {a.slug: a for a in self.awards}   # ещё раз
@property
def other_editions(self): return list(Contest.objects.filter(...))  # запрос на обращение
```

`Story` — 19 свойств, `Chapter` — 6, `ChapterPoll` — 6. Значительная часть —
**презентация**: `format_label`, `format_badge_label`, `updated_label`,
`opens_on_label`, `closes_on_label`, `results_on_label`, `timing_line`,
`eligibility_line`, `char_count_formatted`, `reading_meta_label`. Это работа
шаблонного фильтра или `domain/formatting`, а не модели.

### 2.5 View-слой: ноль Django-форм, ноль декораторов

- `login_required` — **не используется ни разу**. Приватные страницы
  (`/me/`, `/write/*`, `/library/`, `/notifications/`) отдают гостю 200 с пустым
  контекстом. Отсюда `if username else []` — **15 раз** в одном
  `profile_me`.
- `require_POST` — используется один раз (`logout`). Остальные восемь
  POST-эндпоинтов проверяют `request.method != 'POST'` вручную и на GET молча
  редиректят.
- Django-формы — **не используются нигде**. `request.POST.get(...)` встречается
  32 раза, валидация написана руками списками `errors`, `RASTER_ONLY`
  вызывается вручную, потому что валидаторы поля не срабатывают вне ModelForm
  (это прямо признано в комментарии `views/write.py:131`).
  `story_settings` — 60 строк ручного разбора формы.

`ModelForm` убирает здесь порядка 150 строк и заодно чинит валидацию файлов.

### 2.6 Непоследовательный 404

`profile_other` → `Http404`. `story_detail`, `genre_detail`, `tag_detail`,
`collection_detail`, `contest_detail` → **200 с «табылмады»** внутри страницы.
Из-за этого каждый шаблон обязан выдерживать `story=None`, а поисковик
индексирует любой выдуманный slug.

### 2.8 Проза вместо кода

32 % непустых строк Python — комментарии и docstring'и. В `models.py` — 580
строк прозы на 870 строк кода. Комментарии написаны как эссе («Раньше он был
размазан по views.py пятью приватными функциями…») — это **история изменений в
исходнике**, место которой в git log и в реестре решений.

Это не стилистика. Это стоимость: каждая правка кода требует правки абзаца
рядом, иначе комментарий начинает врать. Часть уже врёт (`views/story.py:32`
ссылается на `SAMPLE_PROGRESS` — литерал, живущий теперь только в сиде).

### 2.9 Тесты: 1 156 штук ради ~300 сценариев

Стиль — «класс на состояние страницы, метод на одно утверждение, запрос в
`setUp`»:

```python
class SearchResultsWithMatches(TestCase):
    def setUp(self):  self.response = self.client.get(...)   # ← 4 раза
    def test_200(self): ...
    def test_query_echo(self): ...
    def test_shows_matching_story(self): ...
    def test_no_empty_state(self): ...
```

Django создаёт экземпляр на каждый метод → **четыре HTTP-запроса ради четырёх
утверждений об одном ответе**. Плюс:

- `test_200` дублирует `test_urls_smoke.py` в десятках мест;
- тесты завязаны на литералы корпуса («Алыс жағалауларда», «Рысқали»,
  `aidana`) — правка демо-данных ломает суиту;
- `test_docs_sync.py` делает документацию **исполняемой зависимостью кода**:
  счётчик «1156 тестов в 25 файлах» в `README.md` и `CLAUDE.md` обязан
  совпадать, иначе красный тест. Изменение числа тестов ⇒ правка двух
  markdown-файлов;
- `test_corpus.py` (50) сторожит целостность демо-данных — нужен только
  потому, что корпус подменяет функциональность (§2.1);
- `test_data_facade.py` (4) проверяет, что импорты в `data.py` существуют. Это
  делает интерпретатор.

Скорость не проблема (22,7 с). Проблема — **1 156 точек, которые надо чинить
при каждом изменении разметки**.

### 2.10 Документация: 3 613 строк, 21 файл, встроенное правило самосинхронизации

`CLAUDE.md` — 493 строки, включающие полное дерево проекта с комментариями
к каждому файлу, реестр из ~20 DEC, список 25 тест-файлов, стилистические
правила шаблонов. Это дублирует то, что видно из кода, и обязано обновляться
в том же коммите (правило самой `CLAUDE.md`).

`docs/` содержит два **завершённых** плана миграции (19, 20 — 326 строк),
карту реализации `14` (366 строк «требование → view → шаблон → тест»,
устаревающую при каждом переименовании) и контракт тестирования `15`
(260 строк — описание того, что и так видно в `core/tests/`).

## 3. Целевая архитектура

```
core/
├── domain/        ← без изменений: правила, константы, чистые функции
├── models.py      ← только поля, Meta, __str__, инварианты и мутации.
│                    Презентация → templatetags/domain.formatting.
│                    Списочные свойства → менеджеры/аннотации.
├── managers.py    ← NEW: StoryQuerySet (public/with_reading_effort/for_catalog),
│                    ContestQuerySet, заменяет половину queries/*.py
├── queries/       ← остаётся только там, где запрос не выражается менеджером;
│                    ВСЁ возвращает QuerySet, не list. AuthorFacts исчезает.
├── forms.py       ← NEW: StoryForm, ChapterForm, ProfileForm, SubmissionForm,
│                    CommentForm. Убирает ~150 строк ручного разбора.
├── links.py       ← без изменений
├── views/         ← @login_required / @require_POST, формы, get_object_or_404
└── tests/         ← ~10 файлов, ~250 сценарных тестов
```

Ключевые смены контракта:

1. **Фасад `data.py` отдаёт QuerySet.** `AuthorFacts` удаляется, параметр
   `facts=` уходит из девяти сигнатур.
2. **Аннотации перестают быть скрытыми.** Либо запрос всегда приходит из
   менеджера, который их ставит (`Story.objects.for_catalog()`), либо свойство
   падает громко, а не уходит в N+1.
3. **Приватная страница отвечает 302, публичная несуществующая — 404.**
4. **Модель не форматирует строки.**

## 4. Пошаговый план

Порядок обязателен: шаги 1–2 сокращают то, что дальше пришлось бы
переписывать дважды. Каждый шаг — отдельный коммит, суита зелёная после
каждого.

- [x] **1.5** Счётчик оқылым: `record_story_view` двигает `views` и
