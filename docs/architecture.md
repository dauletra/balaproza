# Архитектура

Что такое Balaproza, из чего она собрана и какие инварианты нельзя нарушать.
Почему решения именно такие — [`10-resolved-decisions.md`](10-resolved-decisions.md).

## Продукт

Литературная UGC-платформа на казахском языке: чтение, письмо, конкурсы.
Образовательный контент («Авторлар мектебі») живёт во внешних каналах, на
сайте — только блок ссылок (DEC-02).

**Аудитория — внутренняя информация, продукт её не называет** (DEC-47).
Возрастного ценза у платформы нет: вилку ставит конкретный конкурс (BR-48).

Входит: авторизация, главная, каталог (поиск, жанры, теги, жинақтар),
страница произведения с чтением, авторский кабинет, профиль, библиотека,
уведомления, конкурсы, 5 правовых стабов, системные компоненты.
Не входит: монетизация, личные сообщения, нативные приложения, кастомный UI
модерации (её ведёт Django admin — DEC-23), внутренняя страница школы (DEC-22).

## Стек (DEC-29)

Django 6 с серверным рендерингом шаблонов · PostgreSQL · Tailwind CSS v4 через
`@tailwindcss/cli` (токены в `@theme` внутри `static_src/input.css`, конфига нет) ·
Alpine.js 3 и htmx 2 как self-hosted `<script>` · self-hosted variable WOFF2.
JS-сборщика, ES-модулей и клиентского стора нет и не планируется: интерактивность
точечная. Свой JS — простыми файлами в `static/js/` (`Alpine.data` по имени),
инлайновых `<script>` с логикой в шаблонах нет.

## Слои

```
core/domain/    правила: константы и чистые функции. Моделей и запросов не знает
core/managers.py  выдача: StoryQuerySet и ContestQuerySet — публичность, состав
                карточки, объём чтения, оси каталога, фазы конкурса
core/queries/   записи: сборка выдачи из менеджеров, справочники и мутации
core/data.py    фасад: единственная дверь к данным для views, контекст-процессоров
                и фильтров
core/links.py   «данные + URL»: CatalogState, CATALOG_AXES, сборка ссылок
core/views/     модуль на раздел, имена собраны в __init__
templates/      всё в корневой templates/, не в core/templates/
```

Инварианты слоёв:

- **`core/domain` не импортирует модели, `core.data` и демо-корпус.** Иначе цикл
  импортов и невозможность взять константы в миграцию.
- **Читающая и пишущая стороны ходят через `core.data`.** Ни views, ни шаблоны
  не пишут в модели напрямую.
- **Демо-корпус (`_corpus.py`) читает только `seed_demo`.** Страница, читающая
  литералы, показывала бы не то, что лежит в базе.
- **URL не спускаются ни в слой данных, ни в шаблон.** Каталожные ссылки строит
  `links.py`: собранный руками в шаблоне адрес терял уже выставленные оси.

## Данные

Поля описаны в `core/models.py`, у каждого причина рядом. Здесь — то, чего список
полей не выражает.

| Модель | Что нельзя сломать |
|---|---|
| **User** | Роли «читатель» нет (DEC-01): любой вошедший читает, пишет, комментирует, сохраняет и подаёт на конкурс. `followers` — колонка, но пересчитывается по строкам `Follow` |
| **Genre** | Закрытый справочник 12 (DEC-11), приезжает миграцией `0002` |
| **Tag** | До 10 на работу (BR-TAG-01), путь `pending → accepted\|rejected`, оба счётчика — аннотации (DEC-53) |
| **Story** | `OnProcess` — состояние продолжения, а не модерации. Публичность — `PUBLIC_STATUSES`, не литерал `'Published'` (DEC-37). `format` выбирает автор (DEC-28). `audience` без дефолта: пусто значит «не выбрана» (BR-10b). Число частей — производное (DEC-51) |
| **Chapter** | Нумерация с единицы, текст в `body`, `char_count` считается при сохранении. Чтение через `?chapter=N`, отдельного маршрута нет (DEC-30) |
| **Contest** | Хранятся три даты; фаза, отсчёт, год и число заявок выводятся (DEC-45, BR-40a). Выпуск — отдельный объект, связь через `series` (BR-47) |
| **Submission** | Одна на автора и конкурс (BR-23) — ограничение базы. `submitted_on` — дата, подпись выводится (BR-41a) |
| **LibraryEntry** | Три непересекающиеся полки (BR-60/61). Номера главы здесь нет — закладку держит `ReadingProgress` (DEC-52) |
| **StoryComment** | Один уровень ответов (BR-30), якорь к главе через `chapter_number` |
| **Notification** | Хранит, когда событие было, а не как давно (BR-70a); ведёт к своему предмету (BR-72a) |

**Производное не хранится.** Ни `Genre.count`, ни число частей, ни счётчики тега,
ни фаза конкурса, ни знаки автора (BR-ACH-01): хранимое производное расходится
молча — «87 өтінім» стояло при одной заявке, «0 бөлім» при пяти написанных главах.

Исключения — **акты**, у которых есть дата и автор, и **колонки, по которым идёт
`ORDER BY`/`WHERE`**: `AwardGrant` (решение жюри, DEC-46), `Notification.outcome`
(решение модератора, BR-72b), `Story.likes` и `User.followers` (пересчитываются
по строкам, а не сдвигаются на единицу — так они самоисправляются).

**Аннотация или fallback.** Часть свойств моделей читает аннотацию выдачи
(`chapter_count`, `effective_chars`, `my_reaction`, …) и падает в запрос, если её
нет. Аннотации ставит `with_reading_effort()` — то есть они приезжают вместе с
выдачей, а не «когда вспомнишь». Контракт всё равно невидим: забытая аннотация
даёт N+1 при зелёных тестах, и ловит его `test_query_budget` — **новой странице
бюджет заводится сразу**.

**Хелпер отдаёт QuerySet, а не список.** У списка нет ни кэша, ни ленивости: он
выполняется в момент вызова, даже если страница его не покажет. Так каталог
платил запросом за контекстный ключ, которого не читал ни один его шаблон.

## Связи

```
User (1) ──< (N) Story ──< (N) Chapter
Story (N) >── (1..2) Genre          основной + до одного дополнительного
Story (N) >──< (N) Tag              до 10 (BR-TAG-01)
Story (1) ──< (N) StoryComment ──< ответы, один уровень
User (1) ──< (N) LibraryEntry ──> (1) Story     saved | reading | done
User (1) ──< (N) ReadingProgress ──> (1) Story
User (N) >──< (N) User              Follow
Contest (1) ──< (N) Submission ──> (1) Story
Contest (1) ──< (N) ContestAward ──< (N) AwardGrant ──> (1) Story
Collection (1) ──< (N) CollectionItem ──> (1) Story    редакционная курация
Notification (N) >── (1) User       опц. ссылки на actor / Story / Contest
```

## Роли и доступ

Гость читает публичное. Вошедший — автор (DEC-01): всё чтение плюс лайки,
комментарии, библиотека, подписки, жалобы, свой кабинет и подача на конкурс;
правит и удаляет только своё. Модератор работает в Django admin: решения по
работам, теги, конкурсы, жинақтар, «Аптаның кітабы», ссылки школы.

Приватное принадлежит владельцу: библиотека и прогресс чтения (BR-74), комментарий
жюри в заявке (BR-74a). Списки подписчиков и подписок публичны (BR-75).

## Авторизация

Сессию держит `django.contrib.auth`, «кто это» отвечает `request.user`; своего
флага в сессии нет. Views берут вошедшего через `_current_user(request)` (`None`
у гостя), и **слой данных принимает пользователя, а не ник**: `None` значит
«гость», и каждый хелпер отвечает на него пустотой. Защита от open-redirect —
`_safe_next`.

Снимок автора живёт на самом объекте — `User.authored`, `public_works`,
`own_submissions`, `library_entries`, `shelf()`, `reads` (`cached_property`).
Страница профиля спрашивает работы из восьми мест и платит один запрос;
параметра, который надо не забыть передать, для этого не нужно. Снимок живёт
ровно столько, сколько экземпляр, то есть один запрос.

⛔ **Провайдера личности нет.** Telegram Login Widget с проверкой подписи (NFR-25)
заводится при деплое; до тех пор `login_view` подписывает в демо-аккаунт, а
`signup` ведёт в ту же дверь и аккаунта не создаёт. Это единственный пункт,
делающий публичный запуск не «неполным», а небезопасным.

## Тестирование

`core/tests/` — 12 файлов. Приём: класс на вопрос, один запрос в теле теста,
`subTest` для цикла по данным. Точечные данные — `factories.py`; корпус остаётся
там, где нужен объём (смоук и бюджет запросов). Раннер кладёт корпус в тестовую
базу один раз за прогон и только потом снимает клоны для параллельных процессов.
Логин — `login_as` / `login_as_newcomer` из `base.py`, подделывать сессию нельзя.
